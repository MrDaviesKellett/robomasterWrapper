## Per-finding status

### (1) Context manager: DONE

- `RoboMaster.__enter__` returns the robot. `RoboMaster.__exit__` calls `close()`. If the body raised, any exception from `close()` is suppressed so the body's error is the one reported. If the body succeeded, a `close()` error is raised. `__exit__` never suppresses the body's exception (it returns `False`).
- Related hardening: `close()` used to run `stop()` → `cam.stop()` → `robot.close()` in sequence, so a failing `stop()` (for example, the chassis is offline) skipped the SDK close, which is exactly the hang this finding is about. `close()` now tries both stop steps, always calls `robot.close()`, and then re-raises the first stop or camera error. Its return value is unchanged (the SDK close result).
- Docs: README example, `docs/quickstart.md` and `docs/student_guide.md` §1 now use `with RoboMaster() as robot:`. `docs/api_reference.md` has a new row, and the `close()` row is extended. `docs/troubleshooting.md` has a new "The script finishes but never exits" section.
- New README text: "The `with` block calls `robot.close()` for you, even if your code raises an error. Without `close()`, the SDK's background threads keep running and a finished script never exits. If you do not use `with`, call `robot.close()` yourself at the end."
- Not verified on hardware. There is no robot here, so the hang-at-exit itself was not reproduced. The behaviour is covered by fakes.

### (2) SDK log noise on connect: DONE

- Correction to the brief: the SDK does not log under `robomaster.*`. It uses a single logger named **`sdk`** (`robomaster/__init__.py`: `logging.getLogger("sdk")`, level ERROR, with its own StreamHandler). `robowrap._sdk.sdk_loggers()` covers `sdk` and also any `robomaster` / `robomaster.*` loggers, in case they appear later.
- Mechanism (`robowrap._sdk.QuietSdkLogs`): for the duration of the connect, each SDK logger's existing handlers are raised to CRITICAL, `propagate` is set to False (so a student's `logging.basicConfig` does not echo the lines either), and a capture handler records WARNING+ records. Handler levels and propagate are restored when initialization finishes. If the connect is abandoned by `connect_timeout`, they are restored after the late `robot.close()`, so that close's noise is hidden too. The logger's own level is left alone so records are still created and can be folded into our message.
- Folded signal: the first record containing "connection failed" (otherwise the first record) is appended as `SDK detail: <msg> (N more SDK log messages hidden)`.
- Verified against an unreachable route (TEST-NET `192.0.2.1:40923`, default `connect_retries=2`) with the real SDK in `.venv`. Full stdout+stderr of a student script `with RoboMaster() as robot: robot.forward(0.5)`:

```
Connecting to robot via ap on 192.0.2.1 ...
Traceback (most recent call last):
  ...
RuntimeError: Robot could not be connected. Check power, network mode, and serial number. Last error: Robot: Can not connect to robot, check connection please. SDK detail: Robot: Connection Failed, Please Check Hareware Connections!!! conn_type ap, host ('0.0.0.0', 10453), target ('192.0.2.1', 40923). (17 more SDK log messages hidden)
```

  Before the fix, the same run (with `connect_retries=0`) printed 8 raw ERROR lines per attempt between the Connecting line and the error (24 with default retries). The process exits normally after the failure. No heartbeat appears because the failure takes about 7 s, under the 10 s heartbeat interval. The heartbeat is our own `print` and is not affected by the change.
- Upstream observation (not fixed here, SDK-side): every failed attempt also logs `Client: __init__, create Connection, exception: module 'robomaster.config' has no attribute 'DEFAULT_CONN_PROTO'` from `robomaster/client.py:70`. This looks like a bug in `robomaster-sdk-modern`.

### (3) setSpeed: DONE (breaking)

- `RoboMaster.setSpeed` is deleted. No `__getattr__` override was added. Python's own suggestion machinery produces the hint:
  `AttributeError: 'RoboMaster' object has no attribute 'setSpeed'. Did you mean '.set_speed' instead of '.setSpeed'?`
  `set_speed` still raises the existing `ValueError` that names `set_default_speed(...)` and `continuous_drive(...)`. Verified on Python 3.14.9 and 3.15.2.
- `tests/test_public_api.py`: removed `ALLOWED_LEGACY_NAMES` and its use, renamed the test to `test_public_callables_are_snake_case`, and dropped the `robot.setSpeed(...)` assertion from the `set_speed` test.
- `docs/migration_snake_case.md`, new policy bullet: "`setSpeed` was left behind in 0.9.0 and 0.9.1 as a silent delegator to the blocked `set_speed`. It is removed in 0.9.2 and now raises `AttributeError` like the other 36 names. Python’s own hint reads `Did you mean '.set_speed' instead of '.setSpeed'?`, and `set_speed` then raises a `ValueError` that names the two real choices." The table row is now labelled `setSpeed` (removed in 0.9.2).
- README snake_case policy, `api_reference.md` `set_speed` row and `troubleshooting.md` are updated to match.

### (4) macOS Python: DONE

New README subsection directly under the banner:

```
### macOS: your system `python3` is too old

The `python3` that ships with macOS (Xcode command line tools) is Python 3.9, so `pip install robowrap` fails with it. Install Python 3.14 with one of these lines, then run your scripts with `.venv/bin/python`:

- Homebrew: `brew install python@3.14 && python3.14 -m venv .venv && .venv/bin/python -m pip install robowrap`
- uv: `uv venv --python 3.14 && uv pip install robowrap`
```

The Homebrew line creates a venv because Homebrew's Python is externally managed (PEP 668), so a bare `pip install` would be refused. Not run on macOS from here.

### (5) Headless camera: DONE

New `docs/api_reference.md` section, `robot.cam` → "Headless use (SSH, CI, no display)":

> `view()` opens a PySide6 window, so it needs PySide6 installed and a desktop session (a logged-in macOS, Windows, or Linux desktop with a display). It will not work over plain SSH, in CI, or on a headless Raspberry Pi.
>
> Everything else in `robot.cam` works headless: `start()`, `frame()` (the SDK `read_cv2_image` frame, as a NumPy array), `take_photo()`, the audio helpers, and the detection APIs (`detect_person`, `detect_gesture`, `detect_line`, `detect_marker`, `detect_robot`, `follow_line`, `move_to_marker`). Read frames with `robot.cam.frame()` and save or process them instead of calling `view()`.

Checked against the code: PySide6 is imported only in `viewer.py`, and `frame()` calls `camera.read_cv2_image`.
